## 🧭 Tại sao roadmap được thiết kế thế này

### Vì sao backend trước Android (5+ tháng không UI mobile)?

1. **Mental model HTTP/REST từ phía "tạo ra".** Khi bạn build server, bạn quyết định status code, header, body schema. Khi consume bằng Retrofit, mọi thứ là "magic". Học backend trước → bạn biết Retrofit đang làm gì dưới capo.

2. **SQL & database transfer trực tiếp sang Room.** Room (Android local DB) là ORM giống Exposed/JPA. Hiểu SQL + ORM trước → Room chỉ là "version Android của thứ đã biết".

3. **Auth & security mindset.** JWT signing, password hashing, session, CORS — học từ server side mới hiểu sâu. Mobile auth có nhiều bẫy, nếu không hiểu server → security holes.

4. **End-to-end debug.** Bug "app load chậm" có thể là N+1 query, missing index, response 500KB, cache miss, hay Android render chậm? Hiểu cả 2 đầu → debug đúng tầng.

5. **KMP shared module thiết kế tốt hơn.** Phase 5b sẽ share business logic. Đã có Ktor backend → biết models nào reusable, validation nào cross-platform.

### Vì sao Ktor trước Spring Boot?

- **Ktor:** Kotlin-native, ít ceremony, dễ hiểu HTTP/routing thật sự làm gì
- **Spring Boot:** enterprise standard, job market lớn nhưng learning curve dốc, nhiều magic
- **Thứ tự:** Ktor → hiểu rõ cơ chế → Spring Boot → hiểu enterprise pattern → so sánh được

### Vì sao có Phase 4 (Frontend) trước Phase 5 (Android)?

- Web frontend dễ debug hơn (DevTools, hot reload nhanh)
- TypeScript ecosystem mature, document tốt
- Concepts (component, state, data fetching) transfer sang Compose
- Cuối Phase 4 có web client gọi Ktor API → end-to-end fullstack đầu tiên → động lực vào Phase 5

## 📗 Giai đoạn 2 — Cơ sở dữ liệu (Tuần 9–12)

**Mục tiêu:** Hiểu sâu cách dữ liệu được lưu, truy vấn, liên kết. Chuyển Expense Tracker từ JSON file sang PostgreSQL.

### Tuần 9 — SQL fundamentals
- **Phần gốc:** Mô hình quan hệ (relational), set theory, vì sao SQL declarative
- **Việc cần làm:**
  - Cài PostgreSQL qua Docker (`docker run -d postgres:16`)
  - Học SELECT/WHERE/JOIN/GROUP BY/HAVING/ORDER BY
  - Làm 20+ exercises trên [pgexercises.com](https://pgexercises.com) hoặc PostgreSQL Tutorial
- **Bằng chứng:** File `notes/sql-basics.md` + folder `sql-exercises/` với queries

### Tuần 10 — Schema design + indexes
- **Phần gốc:** Normalization (1NF/2NF/3NF), khi nào denormalize, B-tree index, `EXPLAIN ANALYZE`
- **Việc cần làm:**
  - Thiết kế schema cho Expense Tracker: `users`, `categories`, `expenses`, `currencies`, `budgets`
  - Vẽ ERD (dùng dbdiagram.io hoặc DrawSQL)
  - Viết DDL (`CREATE TABLE`), thêm index hợp lý
  - Chạy `EXPLAIN ANALYZE` trên query phức tạp, hiểu output
- **Bằng chứng:** `db/schema.sql` + `db/erd.png` + `notes/indexes.md` (khi nào đánh index)

### Tuần 11 — Transaction + Exposed ORM
- **Phần gốc:** ACID, isolation level (READ COMMITTED vs REPEATABLE READ), dirty read/phantom read, ORM trade-offs (DSL vs DAO)
- **Việc cần làm:**
  - Học Exposed (Kotlin ORM của JetBrains) — DSL mode trước, DAO mode sau
  - Migrate Expense CLI từ JSON file sang Postgres
  - Viết 1 use case có transaction (vd: transfer giữa categories)
- **Bằng chứng:** Expense CLI v3 (Postgres-backed) trên GitHub branch `phase-2/postgres`

### Tuần 12 — Redis + checkpoint
- **Phần gốc:** Cache patterns (cache-aside, write-through, write-back), TTL, cache invalidation problem
- **Việc cần làm:**
  - Chạy Redis qua Docker
  - Cache exchange rate API responses trong Redis (TTL 1h)
  - Benchmark: thời gian gọi API cached vs uncached
  - Học `flyway` để quản lý migration
- **Bằng chứng:** Expense CLI v4 + `benchmark.md` so sánh thời gian

### 🏁 Checkpoint cuối Phase 2
- [ ] Viết được JOIN 3 bảng, hiểu INNER vs LEFT JOIN vs CROSS JOIN
- [ ] Thiết kế được schema 3NF
- [ ] Biết khi nào nên đánh index (cardinality, query pattern)
- [ ] Hiểu transaction + isolation level + race condition
- [ ] Dùng Exposed (DSL + DAO) thành thạo
- [ ] Hiểu cache-aside pattern và cache invalidation problem

## 🚀 Giai đoạn 3a — Backend với Ktor (Tuần 13–19)

**Mục tiêu:** Build và deploy 1 REST API production-grade với Ktor — Kotlin-native, ít ceremony.

### Tuần 13 — Ktor setup + routing
- **Phần gốc:** Plugin architecture của Ktor, request lifecycle, content negotiation
- **Việc:** Setup Ktor project, routing cơ bản, JSON serialization (kotlinx.serialization)
- **Bằng chứng:** `expense-api` project với `/health` endpoint trả JSON

### Tuần 14 — CRUD endpoints
- **Phần gốc:** RESTful resource design, HTTP method semantics (idempotency!), status code conventions
- **Việc:** Implement `/expenses` (GET, POST, PUT, DELETE), `/categories`, `/users`
- **Bằng chứng:** Postman/Bruno collection với 10+ requests + screenshot

### Tuần 15 — Tích hợp Postgres + Exposed
- **Phần gốc:** Connection pool (HikariCP), prepared statements, SQL injection prevention
- **Việc:** Wire database vào Ktor, repository pattern, dependency injection bằng tay
- **Bằng chứng:** API persist data vào Postgres, `notes/connection-pool.md`

### Tuần 16 — Auth (JWT)
- **Phần gốc:** Symmetric vs asymmetric crypto, JWT structure (header/payload/signature), BCrypt password hashing, refresh token rotation
- **Việc:** Endpoint `/auth/signup`, `/auth/login`, middleware verify JWT, protect routes
- **Bằng chứng:** Auth flow test trên Bruno + `notes/jwt-security.md`

### Tuần 17 — Validation + OpenAPI
- **Phần gốc:** Defense in depth, validation tầng nào (controller vs domain), OpenAPI spec
- **Việc:**
  - Validation với `kotlinx.serialization` + custom validators
  - Error handling middleware (consistent error format)
  - **Mobile-aware additions:**
    - Pagination cursor-based (không offset!) cho `/expenses`
    - Idempotency-Key header cho POST
    - `ETag` + `If-None-Match` cho GET (cache)
  - Generate OpenAPI spec, serve Swagger UI
- **Bằng chứng:** Swagger UI screenshot + `notes/mobile-friendly-api.md`

### Tuần 18 — Testing
- **Phần gốc:** Test pyramid (unit > integration > e2e), Testcontainers (Postgres thật trong container)
- **Việc:** JUnit 5, unit test cho service layer, integration test với Testcontainers
- **Bằng chứng:** Coverage ≥ 70% (cài JaCoCo)

### Tuần 19 — Docker + deploy + monitoring
- **Phần gốc:** Container image best practices (multi-stage build, distroless), 12-factor app, observability (logs/metrics/traces)
- **Việc:**
  - Dockerfile multi-stage
  - Deploy lên [Railway](https://railway.app) hoặc [Fly.io](https://fly.io)
  - Cài Grafana + Prometheus metrics (Micrometer)
  - Setup structured logging (JSON logs)
- **Bằng chứng:** Live URL + Grafana dashboard URL + screenshot

### 🏁 Checkpoint cuối Phase 3a
- [ ] API deployed production, có domain riêng
- [ ] Auth flow chuẩn (JWT, BCrypt, refresh token)
- [ ] OpenAPI docs đầy đủ (Swagger UI render được)
- [ ] Pagination cursor + idempotency key implemented
- [ ] Test coverage ≥ 70% với Testcontainers
- [ ] Grafana dashboard hiển thị request rate, latency, error rate

## 🛡️ Anti-drift discipline (cực kỳ quan trọng)

11 tháng là dài. Risk #1 không phải bỏ cuộc — mà là **học xong tuần 6 đã quên tuần 2**.

### Hàng tuần
- 1 commit lên `kotlin-journey` repo (kể cả chỉ là notes)
- 5 dòng vào [PROGRESS.md](/progress): học gì, vướng gì, hiểu chưa
- Nếu vướng quá 1 ngày → hỏi mentor (đừng google vô tận)

### Cuối mỗi phase
- Tự code lại 1 mini project KHÔNG nhìn code cũ → test recall thật sự
- Update memory file của Claude (nói "tôi xong phase X")
- Trả lời checklist năng lực của phase đó (không tự lừa mình)

### Hàng tháng
- Review tổng quan với mentor (mình)
- Điều chỉnh tốc độ nếu cần — KHÔNG bỏ kiến thức gap
- Nhìn lại retrospective ngắn (cái gì work, cái gì không)

### "Visual feedback" thay thế cho backend phase

Bạn không cần UI sớm, nhưng vẫn nên có "thứ nhìn được" sau mỗi sprint:
