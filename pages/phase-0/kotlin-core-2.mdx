## 4.6. Lambda, extension, higher-order, `let`/`apply` — 6h, tuần 7

### 🎯 Sau module này bạn làm được

- [ ] Viết một higher-order function nhận lambda làm tham số cuối, gọi nó bằng cú pháp trailing lambda
- [ ] Viết 2 extension function dùng lại được cho mọi project sau: `String.chuanHoaSdt()` và `Long.formatVnd()`
- [ ] Cầm 12 dòng Ktor routing thật, chỉ đúng từng trailing lambda và nói receiver của nó là gì
- [ ] Nói được khi nào dùng `let`, khi nào dùng `apply` — và vì sao chưa được đụng `run`/`with`/`also`

### 🌱 Vì sao module này tồn tại

Ở C/Java kiểu trường học, muốn hàm đổi hành vi thì bạn truyền cờ boolean hoặc viết thêm một hàm gần giống. Kotlin coi **hàm là giá trị** — bạn truyền thẳng hành vi vào làm tham số. Nhưng lý do thật để học kỹ module này nằm ở Phase 1: **toàn bộ bề mặt Ktor viết bằng trailing lambda và lambda-với-receiver**. `embeddedServer`, `install`, `routing`, mỗi handler — tất cả cùng một hình dạng. Giải mã được cú pháp này bây giờ thì tháng thứ 5 bạn mở docs Ktor ra và *đọc được*; không thì Ktor trông như một ngôn ngữ khác và bạn dừng lại đúng chỗ server bắt đầu.

### Nội dung cốt lõi

- Function type: `(Int) -> Boolean` là một kiểu dữ liệu như `String` — biến giữ được, tham số nhận được
- Lambda: `{ x -> x * 2 }` — khi chỉ có 1 tham số, dùng `it`
- Higher-order function: hàm nhận hàm hoặc trả hàm
- **Trailing lambda** — luật cú pháp: lambda là **tham số cuối** thì được kéo ra ngoài ngoặc; nếu là tham số duy nhất thì bỏ luôn ngoặc
- Extension function: "mọc" hàm mới lên kiểu có sẵn, bên trong `this` là giá trị đứng trước dấu chấm. Nó không sửa class gốc — chỉ là hàm tĩnh được cú pháp hoá đẹp

```kotlin
val ten1 = dsNguoiChoi.map({ p -> p.ten })  // hợp lệ, nhưng không ai viết vậy
val ten2 = dsNguoiChoi.map { it.ten }       // trailing lambda — dạng bạn gặp 100 lần/ngày
```

*Đóng trang này. Gõ lại hai đoạn trên từ trí nhớ. Gõ lại không nổi = chưa hiểu, đọc lại.*

**Lambda-với-receiver, và nó dùng ở đâu thật — 30 phút**

`apply` không phải phép màu: nó là hàm nhận một lambda mà bên trong lambda đó `this` được gán sẵn thành object bạn gọi. Đó gọi là **lambda-với-receiver**. Cùng một cơ chế, phóng to lên quy mô framework, chính là cái người ta gọi là DSL.

```kotlin
routing {
    get("/health") {
        call.respondText("ok")
    }
}
```

Đọc đoạn trên bằng ba câu, không thêm khái niệm mới nào:

1. `routing` là một hàm, tham số cuối của nó là một lambda → lambda được kéo ra ngoài ngoặc, ngoặc rỗng nên bỏ luôn
2. Bên trong lambda đó `this` là object định tuyến của Ktor, nên `get(...)` gọi được mà không cần tên biến nào đứng trước
3. `get` cũng nhận một lambda cuối; bên trong lambda ấy `this` lại là một object khác — object đại diện cho **một request đang xử lý** — nên `call` có sẵn ở đó

**Sự thật:** không có cú pháp riêng nào cho "routing" trong Kotlin. Tên kiểu của receiver đổi theo phiên bản Ktor; cơ chế thì không đổi từ ngày đầu. Việc của bạn ở tuần 7 là **đọc được**, không phải tự viết DSL — tự viết DSL không nằm trong Phase 0.

**Luật chống loạn scope function** — đây là **chính kiến**, không phải gợi ý:

| Scope function | Phase 0 | Dùng khi |
|---|---|---|
| `let` | Dùng | Biến đổi giá trị nullable: `email?.let { ... }` |
| `apply` | Dùng | Cấu hình object vừa tạo xong |
| `run` / `with` / `also` | Chỉ đọc-hiểu | **Cấm chủ động dùng trong Phase 0** |

Vì sao cấm: năm hàm gần giống nhau, chỉ khác ở chỗ `it` hay `this` và trả về cái gì — dùng lẫn lộn tạo ra chuỗi mà chính người viết đọc lại không giải thích nổi. `let` và `apply` phủ trên 90% nhu cầu thật. Ba cái còn lại: gặp trong code người khác thì tra bảng, hết.

### ⚠️ Bẫy

| Bẫy | Vì sao mắc | Dấu hiệu nhận ra |
|---|---|---|
| Nhồi scope function cho "ra vẻ Kotlin" | Code mẫu trên mạng dùng nhiều, tưởng đó là idiomatic | Chuỗi `.let`/`.apply` nhiều tầng; đọc lại không nói được `it` với `this` đang trỏ vào gì |

| Viết extension cho mọi thứ | Mới học thấy hay, "xịn hoá" cả codebase | Extension chỉ được gọi đúng 1 lần, hoặc chứa logic nghiệp vụ lẽ ra thuộc về data class |

## 4.7. Generics đọc-hiểu + exception + Result — 3h, tuần 8

### 🎯 Sau module này bạn làm được

- [ ] Đọc một signature stdlib có `<T>` và dịch thành một câu tiếng Việt trọn nghĩa
- [ ] Chặn input rác ngay cửa hàm bằng `require`/`check` thay vì if-return rải rác
- [ ] Viết hàm trả `Result` để lỗi trở thành giá trị mà caller buộc phải xử lý

### 🌱 Vì sao module này tồn tại

Generics ở trường dạy để thi — wildcard, bounded type, vẽ sơ đồ. Phase 0 chỉ cần mức **đọc thông thạo**: không hoảng khi docs viết `Iterable<T>`, còn `in`/`out` chỉ cần nhận diện. Viết generic của riêng mình không nằm trong 3h này và cũng chưa cần đến hết Phase 0.

Trọng tâm nằm ở nửa sau: **lỗi cũng là dữ liệu** — nối thẳng về sealed class ở module 4.4. Một hàm đọc file có thể thành công hoặc thất bại; cả hai đều là kết quả hợp lệ cần được model, không phải quả bom chờ nổ. Server tháng thứ 5 sống bằng đúng tư duy này: một request hỏng không được phép giết cả process.

### Nội dung cốt lõi

- Đọc `fun <T> ...`: `T` là chỗ trống điền kiểu — một hàm viết một lần chạy cho mọi kiểu
- `in`/`out`: mức nhận diện khi đọc docs (`out` = kiểu chỉ đi ra, `in` = kiểu chỉ đi vào). Không cần viết được
- `try`/`catch`/`finally`, tự định nghĩa exception
- `require` (validate **tham số**) và `check` (validate **trạng thái**) — thất bại sớm, thất bại to

```kotlin
fun rutVang(soVang: Long) {
    require(soVang > 0) { "Số vàng phải dương, nhận: $soVang" }
    // tới được đây nghĩa là hợp đồng đã được kiểm
}
```

- `runCatching` và `Result` — bọc lỗi thành giá trị:

```kotlin
val ketQua: Result<Int> = runCatching { "12a".toInt() }
// ketQua.isFailure == true — lỗi giờ là dữ liệu cầm được, không phải bom
```

`runCatching` bắt **mọi `Throwable`** — kể cả lỗi JVM như `OutOfMemoryError`, `StackOverflowError`, và `CancellationException` của coroutine (gặp ở P1, nó phá structured concurrency). Vì thế `.getOrNull()` mà không nhìn `exceptionOrNull()` chính là catch rỗng trá hình — bị trừ điểm đúng như catch rỗng ở luật bên dưới.

*Đóng trang này. Gõ lại hai đoạn trên từ trí nhớ, đoán output trước khi chạy.*

**Luật cứng của module: cấm nuốt exception bằng catch rỗng.** Mọi `catch` phải hoặc xử lý có nghĩa (trả giá trị mặc định *có chủ đích*, báo người dùng), hoặc log rồi rethrow. Catch rỗng không sửa bug — nó chôn bug xuống ba tầng đất, để dữ liệu sai âm thầm lan ra và phát nổ ở chỗ khác, khó lần hơn gấp mười. Khi chấm Project 2, catch rỗng bị trừ thẳng vào mục chất lượng code. Không thương lượng.

## 4.8. Interface + composition — 2h, tuần 9

### 🎯 Sau module này bạn làm được

- [ ] Giải cùng một bài bằng kế thừa rồi refactor sang composition, chỉ ra bản nào dễ thay đổi hơn và vì sao
- [ ] Đưa phần chạm ổ đĩa ra sau một interface để test chạy được mà không cần file thật

### 🌱 Vì sao module này tồn tại

OOP thi cử đặt kế thừa làm trung tâm. Kotlin cố ý làm class `final` mặc định — ngôn ngữ đang nói thẳng với bạn: **kế thừa là ngoại lệ phải xin phép, không phải mặc định**. Module này chỉ có 2h và chỉ làm một việc: cắt được ranh giới giữa *cái gì* và *bằng cách nào*. Tuần sau bạn bắt đầu Project 1; tháng thứ 6 chính ranh giới này là thứ giữ `caro-engine` sạch I/O.

### Nội dung cốt lõi

- Interface = hợp đồng hành vi; class = một cách thực hiện hợp đồng
- **Composition over inheritance** — không học thuộc khẩu hiệu, làm thật: giải một bài bằng kế thừa, refactor sang composition, đặt hai bản cạnh nhau so sánh

```kotlin
interface NguonThoiGian {
    fun homNay(): LocalDate
}
// Code dùng NguonThoiGian không biết — và không cần biết — ngày đến từ đâu.
// Bản thật đọc đồng hồ máy; bản test trả về ngày cố định 29/02/2024.
// Nhờ vậy test "năm nhuận" chạy được vào bất kỳ ngày nào trong năm.
```

Ví dụ này ở **domain khác** với bài tự kiểm bên dưới — cố ý. Nó minh hoạ một điều duy nhất: interface tách *cái gì* khỏi *bằng cách nào*, và chính chỗ tách đó là nơi test chen vào được. Khi áp lên code của bạn, phần khó không phải cú pháp `interface` mà là câu hỏi: **ranh giới nên cắt ở đâu?** Cắt sai chỗ thì có interface mà vẫn không test được.

*Đóng trang này. Gõ lại đoạn trên từ trí nhớ, rồi tự viết thêm một class implement nó.*

### ⚠️ Bẫy

| Bẫy | Vì sao mắc | Dấu hiệu nhận ra |
|---|---|---|
| Kế thừa để tái sử dụng code | Trường dạy kế thừa là trung tâm OOP | Class cha tên `Base...` chung chung; class con override để *vô hiệu hoá* hành vi cha |
| Interface cho mọi class | Mới học thấy hay, "kiến trúc hoá" cả bài tập | Interface chỉ có đúng 1 class implement và sẽ mãi như vậy |
| Tách file kiểu cắt cơ học | Tách theo số dòng, không theo trách nhiệm | Các file mới import chéo nhau lòng vòng; sửa 1 tính năng vẫn phải mở 4 file |
